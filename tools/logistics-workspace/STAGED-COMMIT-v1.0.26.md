# v1.0.26 大快照提交与回执核查

## 真实事件证据

截图显示固定批次：仓库报价31113、区域报价4091、模板571；305/305上传片已确认，失败阶段为 `[commit]`，HTTP503且响应不是JSON。它不是本次发布成功回执。

只读服务端核查发现对应任务约39,973,341字节、305个上传片，尚无receipt；GitHub已写有24个加密数据批次，根快照仍是402887770f。未读取密钥、未导出或打印业务报价、未修改真实任务。

旧流程虽分片上传，但commit仍在一个请求中完成全部分片重建、全部GitHub批次的检查/写入/读回，以及最终完整快照再次组装。有限资源模型能复现先写入一部分批次、最终索引未切换的失败；因此不能把“305片已确认”当成“展示快照已发布”。没有捕获到同事该次Worker资源异常日志，不能声称已由日志证明某一特定平台限额就是唯一原因。平台约束参考：https://developers.cloudflare.com/workers/platform/limits/

## 修复

- 上传协议、任务ID、账户隔离和已有305片保持兼容；保留本机主库及IndexedDB命名空间。
- commit按窗口发布，每个请求最多处理3个512KiB展示批次；进度存回原任务。前端自动续提，可暂停、刷新页面后恢复。
- 已写入GitHub的批次仍按摘要读取核验后复用；进度保存失败或响应丢失不会要求重传上传片。
- 所有批次核验后才用原GitHub CAS切换根索引。最终回读核对根SHA、操作ID和整个快照摘要，避免在单次请求里再次下载所有展示批次。
- 大快照基线不再启用旧的整份基线重组增量路径；后续使用完整本机投影分阶段发布。此前针对小基线创建的冻结增量任务仍可继续。
- 查询上传进度只读元信息；重建时分批解密到一个缓冲区，写展示批次时流式序列化，仅保留当前窗口，减少同一完整快照的多份副本。
- 输入端持久显示“最近核验成功的发布”数量、SHA和时间，明确它不是当前进行中任务的成功证明。commit网关异常不再错误指向重启已工作的本机中继。

## 回归证据及限制

虚拟任务严格匹配31113/4091/571、39,973,341字节、305上传片，并预置24个独立GitHub加密批次。有限预算内成功续提，最终根只写一次；每请求最多21次被测服务调用（未包含生产入口认证/配额调用）。完整下载后的原始字节SHA-256与输入一致。

覆盖：提交进度保存失败、根写成功但回执丢失、重入、客户端暂停续提、旧冻结增量、篡改摘要、现有用户/权限隔离、失败不清理任务、成功回执跨状态刷新和重新打开保留。全部数据为虚拟，不向生产发布测试快照。这些结果不等于同事真实任务已发布完成。

## 发布与恢复

先部署Worker，再发布v1.0.26应用及自动更新清单。录入电脑在原文件夹、原浏览器升级后，打开原冻结任务点击“继续上传”；不要改发、重导入或清理浏览器数据。大快照全部提交完成后才会出现新成功回执。展示端随后刷新。

回滚：恢复此前Worker及前端应用文件；保留任务与批次。checkpoint和pendingReceipt仅新增任务元数据，原数据/加密配置/根快照格式不迁移。旧v1.0.25前端不识别pending进度，应用回滚后不应把其“缺少核验回执”当作成功；升级再继续即可。
